# Lago API and operation matrix

Evidence baseline: Lago OpenAPI 1.51.0, Lago human documentation, and the disposable free self-hosted/Cloud observations recorded in [AUDIT.md](AUDIT.md). The node targets Lago REST API v1 under `/api/v1`.

Every action is a programmatic exception (`execute()` → per-input shared router → resource handler → n8n authenticated request helper). A single node cannot mix active `execute()` and declarative operation routing: `execute()` bypasses that routing. The shared transport also maps Lago-specific 401/403/404/422 and network failures, downloads can conditionally follow an empty POST with GET, and the router preserves pairing and Continue On Fail. Therefore the node has no `requestDefaults` or `routing` metadata. “U/I” means the matching unit and disposable-Lago integration suites.

## Known evidence gaps

The resource suites prove request shapes, response unwrapping, pagination cases, and operation-specific behavior. Focused router tests prove deterministic multiple-input order, multi-record pairing, frozen-input preservation, Continue On Fail, and fail-fast behavior; transport suites prove request-helper use and mapped errors. On 2026-09-08, the pinned disposable Lago v1.51.0 stack passed all 14 integration files and 169 tests; teardown then removed its test containers, network, volume, and generated environment files. Input immutability is enforced at the shared-router boundary rather than exhaustively for every handler, and there is no exhaustive credential-redaction corpus for every possible upstream/network error shape.
